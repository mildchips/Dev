# Финансовая сверка v0.3.6

## Два независимых контура

Новый `Finance` принимает только локальный контракт `aipo.normalized-finance/1`. Существующий импорт нормализованных CSV/XLSX сохраняет прежнюю семантику; старые суммы не смешиваются с новым журналом, не мигрируют в него автоматически и не получают статус «Сверено» автоматически. API staging v0.3.5 также остаётся отдельно.

Новый экран показывает суммы финансовых начислений, вклад после указанных расходов и COGS. Это не чистая прибыль: состав налогов и всех затрат бизнеса не подтверждён. Совпадение с загруженным эталоном не является доказательством подлинности отчёта или независимости источника. Эталон передаётся оператором отдельно; программа не строит его из собственных операций.

## Формат отчёта

Точные образцы: `examples/finance_v036/*.json`. Обязательные поля верхнего уровня:

| Поле | Значение |
|---|---|
| contract | `aipo.normalized-finance/1` |
| report_id | неизменяемый ID отчёта внутри магазина |
| provider | `WB` или `Ozon`, совпадает с магазином |
| start, end | даты ISO YYYY-MM-DD, включительно |
| complete | boolean, заявление оператора о полноте загрузки |
| events | до 15000 операций; файл до 5 МиБ |

Обязательные поля события: `event_id`, `date`, `sku`, `type`, `amount`, `quantity`. Дополнительные: `posting_id`, `batch_id`, `reverses`. Новые поля, неизвестные категории или версия контракта отправляют строку в карантин. Сумма — десятичная строка с максимум двумя знаками или целое число рублей. Float, NaN, экспоненциальная форма и дробные копейки отклоняются. ID всегда строковый, в том числе WB rrdId >2^53. Валюта локального контракта фиксирована RUB; конвертации валют нет.

| type | Правило |
|---|---|
| sale | Сумма ≥0, SKU, целое количество >0 |
| return | Сумма ≤0, количество <0, ссылка `reverses` на исходную продажу того же SKU/партии; общий возврат не превышает проданное количество |
| storno | Точная полная обратная операция к продаже или расходу/возмещению; совпадают SKU, отправление, противоположная сумма; при отмене продажи — противоположное количество. Сторно возврата и цепочки сторно пока не поддерживаются |
| fee | Комиссия/сбор; исходный знак сохраняется, положительная корректировка разрешена |
| storage | Хранение; исходный знак сохраняется |
| delivery | Доставка; исходный знак сохраняется |
| refund | Положительное возмещение расхода, не возврат товара покупателем |
| other | Явно проверенное оператором прочее начисление; сюда автоматически ничего не классифицируется |

Неправильная ссылка возврата/сторно блокирует вклад; статус сумм получает расхождение при выявленной ошибке связи. Отсутствующая себестоимость не мешает открыть приложение или сверить денежные суммы.

## Источники и отсутствие дублей

Ключ события `(store_id,event_id)`; provider неизменно задан магазином. Сохраняются JSON нормализованного события, SHA-256 нормализованного содержимого, SHA-256 исходной JSON-строки, сигнатура состава и типов полей, версия контракта и время импорта. SHA исходного события канонизирует JSON, поэтому пробелы и порядок ключей не считаются изменением. `finance_schema_observations` хранит историю увиденных сигнатур, `finance_contracts` — определение утверждённой версии. Полное тело ошибочного события не записывается в карантин: только причина и хеши.

Повтор одного события не увеличивает сумму. Пересекающиеся отчёты ссылаются на одно событие, но имеют отдельные контрольные итоги. Итоги пересекающихся отчётов не суммируются. `overview.unique_accruals_kopeks` считает уникальные события магазина, но сам по себе не означает сверенную прибыль.

Импорт каждого файла атомарен. Валидные события и записи карантина сохраняются одной транзакцией. Изменённое содержимое при том же ID не перезаписывает исходное событие: конфликт блокирует сверку соответствующего отчёта. Новые события в завершённом отчёте запрещены. После `complete=true` повтор частичной страницы не отменяет завершённость. Коррекции передаются новыми ID со знаком и ссылкой. Journal/controls/contracts/batches защищены от UPDATE на уровне SQLite. Удаление магазина по существующему подтверждённому сценарию удаляет его записи; это не юридически неизменяемый архив или SIEM.

## Контрольные итоги

Файл контроля содержит `reference_id`, `total`, `categories`, `postings`. Сумма категорий должна совпадать с total. Сверка сравнивает категории и общую сумму до копейки; разные категории с одинаковым итогом не дают ложное подтверждение. При переданной разбивке `postings` проверяются все перечисленные и фактические отправления. Расходы без отправления остаются общими и не приписываются SKU/отправлению.

Контрольные файлы сохраняются исторически; используется последний. Их изменение не меняет исходные операции. Хеш контрольного файла и его ID отображаются в API. Если оператор загрузил пересчитанный по тем же операциям эталон, программа не может установить его независимость.

| Статус | Условие |
|---|---|
| Расхождение | несовпадение total/categories/postings, карантин, некорректная обратная операция |
| Частично загружено | ошибок выше нет, но `complete=false` |
| Данные в процессе проверки | нет эталона или нет финансовых строк |
| Устарело | после последней сверки прошло более 24 ч |
| Сверено | завершённый непустой отчёт совпал с эталоном, ошибок нет, сверка свежая |

Приоритет именно такой: частичная загрузка с уже выявленной ошибкой показывает «Расхождение». Исторический период всегда указан отдельно; «Сверено» не утверждает, что загружены все операции на текущую дату.

## Историческая себестоимость и партии

При `batch_id` берётся только партия этого магазина/SKU, поступившая не позже исходной продажи; проверяется приобретённое количество по уникальным продажам всей базы магазина. Повтор в другом отчёте не расходует партию повторно. Автоматического FIFO/LIFO нет. Возврат восстанавливает COGS по партии/дате исходной продажи, а не по текущей цене. При отсутствии партии используется история `cost_revisions` с последней датой ≤дате исходной продажи; статическая текущая цена не подставляется в прошлое автоматически.

Количество партии консервативно ограничивает суммарные продажи: возвращённые/сторнированные единицы пока не допускаются к повторной продаже в той же партии. Это защитное ограничение до отдельного складского allocation ledger. Изменять использованную партию нельзя — требуется новая партия; исправление ошибочной привязки источника пока через отдельную процедуру будущего релиза.

Если себестоимость неизвестна, превышен объём партии или неверна ссылка — вклад отчёта и SKU скрывается. После сверки COGS определяется как Σ(знаковое количество × цена исходной продажи). Вклад отчёта = начисления − COGS. Вклад SKU не включает общие расходы и не называется чистой маржой. Карантин автоматически не очищается: безопасная ревизия/переклассификация запланирована на v0.3.7.

## HTTP/API

Все пути защищены существующими localhost/Host/auth/CSRF проверками.

| Метод и путь после `/api/stores/{id}` | Назначение |
|---|---|
| GET `/finance` | Отчёты, состояния, партии, уникальные события |
| GET `/finance/journal?limit=100` | До 1000 событий магазина с источниками и хешами |
| POST `/finance/reports` | Multipart file: нормализованный JSON |
| POST `/finance/controls` | Multipart file + report_id: отдельный эталон |
| POST `/finance/batches` | Multipart file: партия |

Числа копеек в HTTP представлены десятичными строками для точности JavaScript. Загружаемый JSON не допускает повторяющихся ключей.
