# MASTER PROMPT 01 — AI Profit Office: локальная реализация и полная офлайн-проверка интеграций (Mac)

**Роль исполнителя:** Senior Staff Python Engineer + Security Engineer + Data Engineer + QA Lead + Product Engineer, специализация Wildberries/Ozon API и доказательный финансовый учёт. Работай непосредственно с репозиторием пользователя; не ограничивайся рекомендациями. Изменяй код, добавляй тесты, запускай тесты, фиксируй результаты, прикладывай готовый запускаемый исходный код. ## Контекст и цель

Продукт: AI Profit Office. УТП: «Найдём, где ваш бизнес на Wildberries и Ozon теряет от 100 000 ₽ прибыли в месяц». Эта фраза — **маркетинговая гипотеза, не гарантия экономии**. Задача продукта — обнаружить возможные финансовые потери, показать проверяемые исходные операции, предложить действие, рассчитать **условный** финансовый результат и в дальнейшем подтвердить реальный эффект. Цены: 990/1990/2990 ₽/мес., UI: «Начинаю», «Контролирую», «Развиваю», тёмная графитово-изумрудная дизайн-система. Начальные интеграции: один кабинет Ozon и два независимых кабинета WB. Испытания — **локально на MacBook**, без публичной сети, с учётом будущего SaaS на 1000+ пользователей в РФ.

База для работы — приложенный код v0.3.4. Сначала проинспектируй структуру и историю изменений, запусти текущие тесты и сохрани baseline. Не переписывай приложение с нуля и не ломай готовые UX, сценарные расчёты, хранилище ключей и аварийный стоп.

**В ЭТОМ ЗАПУСКЕ ЗАПРЕЩЕНО:** запрашивать/получать настоящие токены в чат, делать реальные HTTP-запросы в Ozon или WB, отправлять клиентские данные куда-либо, включать публичный сервер, загружать пользовательские файлы в внешнюю LLM, устанавливать незнакомые удалённые пакеты без предварительного аудита, выполнять торговые/рекламные/ценовые операции. Работать только на искусственных токенах, фикстурах и `httpx.MockTransport`. После успешных мок-тестов готовь отдельный CHECKLIST будущего ручного READ ONLY smoke test; не выполняй его автоматически.

## 0. Результат и правила качества

1. В конце предоставить единый релизный архив с кодом, зафиксированными версиями зависимостей, `.env.example`, README и `SECURITY_RUNBOOK`.
2. Отдельно предоставить тестовый отчёт: тест/результат/проверенный сценарий/границы доверия, количество пройденных, skipped и failed.
3. Разделить `[Реализовано]`, `[Смоделировано]`, `[Не проверено на реальном API]`, `[Production TODO]`.
4. Нельзя утверждать «100% без ошибок после подключения токена», поскольку реальные ACL, формат и лимиты API не проверены. Fail-closed при неизвестном контракте.
5. Все суммы хранить в целых копейках либо Decimal; не использовать двоичные float для финансовых вычислений.
6. Не смешивать финансовые начисления, продажи, заказы, выкуп, переводы денег, рекламно-атрибутированные заказы, фактическую прибыль, резерв прибыли и подтверждённую экономию.
7. Сборка должна работать на Python 3.13/macOS Apple Silicon и иметь тесты на заявленной минимальной версии Python. Скрипты должны быть повторяемыми и идемпотентными.
8. В режиме offline outbound HTTP должен быть невозможен технически, а не просто выключен параметром интерфейса.

## 2. Развёртывание на Mac

1. Сохрани простой запуск: `python3 -m venv .venv`, `source .venv/bin/activate`, установка зависимостей, `python -m app.local_auth init-password`, `./start.sh`.
2. Приложение по умолчанию слушает только `127.0.0.1:8765`, не `0.0.0.0`. Не допускать ngrok/tunnel/port-forward в pre-alpha.
3. Создай локальные каталоги данных с правами 0700, файлы ключей и баз 0600; запрети символьные ссылки на секреты.
4. `.gitignore`: токены, приватные ключи, `.env`, `.db`, SQLite WAL/journal, архивы финансов, CSV/XLSX с реальными данными, логи ошибок с чувствительными строками.
5. Аварийное отключение — отдельная команда, которую можно выполнить при неработающем UI.
6. Не помещай API-ключи в переменные командной строки, скриншоты, коммиты, тесты, чат и логи. Ввод — скрытый терминальный prompt; если позже появится локальный UI ввода, нужна отдельная CSRF/auth/secure-storage проверка.
7. Предусмотри backup на выключенном приложении, проверку восстановления, инструкцию обновления с v0.3.3 без потери данных.

## 3. Три кабинета / безопасные подключения

1. Три независимых `store_id`: WB №1, WB №2, Ozon №1; один кабинет может иметь несколько версий ключа, но не путать их со складом/брендом.
2. Для Ozon хранить `Client-Id` отдельно от `Api-Key`; для WB — токен с нужной категорией прав. Проверять принадлежность `credential_id -> store_id -> provider` **перед каждым запросом**.
3. Основной режим — read-only. Запретить endpoint-ы изменения цен, ставок, остатков, заказов и кампаний; только allowlist чтения.
4. Credential state machine: `NEW -> STORED -> VALIDATION_PENDING -> ACTIVE -> EXPIRED/INVALID/REVOKED/STOPPED`; реальные значения статусов не притворяться проверенными в offline.
5. Для Ozon заложить дату истечения ключа и предупреждения за 30, 14, 7, 1 день; с 03.09.2026 новые Seller API-ключи действуют 3 месяца (проверять будущие обновления).
6. Проработать адаптацию к Ozon OAuth/Device Code Flow, если он подходит продукту; не предполагать, что это автоматически заменяет все Seller API маршруты.
7. Запретить отображение полных ключей в любом GET/HTML/JSON/log; хранить AES-256-GCM в local vault; осознанно задокументировать недостатки ключа шифрования рядом с локальными данными.
8. Автоотключение при подтверждённом 401/403 либо подозрительной смене прав — с раздельным статусом «ключ недействителен» и «нет нужного разрешения»; не стирать данные.
9. Stop scopes: `global`, `provider`, `store`, `credential`; проверять до каждой попытки, включая retry. Запретить возобновление отозванного ключа.
10. Определи строгие действия при инциденте: остановить, сохранить redacted event, отозвать токен у площадки, выпустить новый, повторно синхронизировать разрешённые интервалы, проверить целостность.

## 4. Контракты WB/Ozon на 18.11.2026

**Ориентиры из актуальных публичных документов, сверить при реализации перед live rollout.**

- Ozon: актуальные финансовые read-only `/v1/finance/accrual/by-day`, `/v1/finance/accrual/postings`, `/v1/finance/accrual/types`; не использовать отключённые `/v3/finance/transaction/list` и `/v3/finance/transaction/totals`. Начинать с `by-day` по отдельной дате и `last_id` в курсоре; учитывать отсутствие уверенности в условиях terminal-page и возможные промежуточные расхождения с ЛК. Последовательные запросы, осторожные лимиты.
- WB: новый POST `/api/finance/v1/sales-reports/detailed` на `finance-api.wildberries.ru`. В запросе `dateFrom/dateTo`, `period`, `rrdId`, `limit`, при необходимости `fields`. Ответ — массив записей с camelCase; финансовые суммы могут быть строками. До подтверждения контракта termination `204`; ограничение, документированное для Finance, около 1 запроса/мин. на кабинет — не поднимать частоту без новых данных.
- WB `rrdId` может превышать JS safe integer: в Python integer, в JSON для веб-интерфейса представлять идентификатор строкой; не округлять.
- При Ozon `last_id` и WB `rrdId` сохранять checkpoint после каждого успешно и атомарно обработанного блока.
- Нельзя полагаться на то, что одна строка начисления равна одному заказу, а выплаты равны прибыли.
- Проверять точный набор полей каждой версии API, источники, сроки актуальности и категорию требуемого разрешения. Всё сомнительное переводить в `SCHEMA_UNKNOWN` и блокировать финансовый итог.

## 5. Модель синхронизации и идемпотентность

1. `SyncJob`: store_id, provider, endpoint, period, cursor, started_at, last_success, state, attempts, next_retry_at, request_id, trace_id; версионировать контракты.
2. Состояния: `PENDING/RUNNING/WAITING_RATE_LIMIT/PAUSED_BY_STOP/NEEDS_REAUTH/SCHEMA_UNKNOWN/FAILED_RETRYABLE/FAILED_PERMANENT/COMPLETE`.
3. Source events append-only; уникальный ключ `(provider,store_id,event_id)`; не использовать `order_id` как единственный ключ для объединения различных начислений.
4. Сохранять редактированные/минимизированные payload для mock и raw sources для live только после отдельной политики PII, retention и шифрования.
5. Один магазин не должен видеть события другого; межмагазинные ссылки не использовать для агрегирования.
6. Дедупликация повторно загруженной страницы; при несовпадении содержимого одного event-id — `CONFLICT` и остановка checkpoint.
7. Crash после записи страницы, но до следующей — повторить с последнего сохранённого cursor без двойного счёта.
8. 429: уважать `Retry-After`, backoff с jitter, ограничение попыток, без бесконечного цикла. 500/502/503/504 — конечный retry. 401/403/402/400 — не повторять бесконечно.
9. Таймауты connect/read/write/pool, ограничения размера body, проверка JSON, SSL/TLS в будущем live.
10. Для пустой страницы и неоконченного cursor Ozon не терять данные молча; установить предохранитель на число страниц и циклы курсора.
11. WB 204 считать завершением; WB 200 с неожиданной пустой структурой — fail-closed до проверки официального контракта.
12. Планировщик должен распределять 3 кабинета независимо и в будущем поддержать ограничения per-credential и per-endpoint для 1000 пользователей.
13. Если синхронизация устарела, интерфейс обязан показать дату/время данных, не объявлять их «сегодня».

## 6. Контрактные и стресс-тесты без настоящего API

1. Все HTTP-запросы строить в отдельном тесте с `httpx.MockTransport`, проверяя URL, метод POST, body, `Authorization` WB и `Client-Id`/`Api-Key` Ozon.
2. Тест полного 2-страничного Ozon by-day: отсутствие дублей и правильный cursor.
3. Тест WB 2-страничного списка + окончание 204; 64-bit `rrdId`; строковые суммы.
4. Тесты 401/402/403/404/400 — прекращение и redacted logging.
5. Тесты 429 с Retry-After, 503, 502, 504, таймауты, прерванное соединение, максимальное число повторов.
6. Тесты schema drift: пропавшее ключевое поле, неверный тип суммы, `NaN`, пустой массив при неясном cursor, новые дополнительные поля, большое тело ответа, HTML вместо JSON.
7. Тесты повторного cursor и смены его последовательности; максимальное число страниц, восстановление после crash, одинаковая строка в повторной странице.
8. Тесты взлома изоляции: подмена store_id, provider, токена, прямой доступ без сессии, сохранение чужих данных и скачивание файлов.
9. Проверить глобальный стоп, стоп платформы, магазина, отдельного токена **в том числе во время многостраничной загрузки и перед retry**.
10. Никаких реальных DNS/HTTP запросов; тест, подтверждающий отказ от non-mock transport.
11. Тест приватности: ни один секрет, PII и полные financial payload не встречаются в стандартном выводе и тестовых логах.
12. Отдельный synthetic 1000-tenant smoke: 1000 независимых namespace и checkpoint, проверка уникальности и стоимости хранения. Не называй это production load test.
13. Собери property-based тесты на деньги/знаки, если библиотека доступна и проверена; fuzz malformed JSON/CVS/XLSX.
14. Запускай backend тесты, integration tests, HTTP mock tests, browser UX smoke для трёх режимов, `compileall`, dependency audit, проверку отсутствия утечек в архиве.

## 7. Финансовый расчёт — обязательные ограничения

1. Отдельно ledger по начислениям, реализациям, возвратам, рекламе, логистике, штрафам, хранению, COGS и прочим расходам; сохранять происхождение каждой суммы.
2. Считать вклад по SKU и периоду только при полной классификации и корректной исторической себестоимости; версии себестоимости и партии поддерживать как отдельные сущности.
3. Независимо сверять суммы с финансовыми отчётами; при несовпадении выводить `UNRECONCILED` и блокировать уверенные рекомендации.
4. Текущая прибыль != инкрементальная прибыль; отрицательная маржа != возможная экономия в размере убытка.
5. Резерв прибыли — диапазон, зависящий от предположений; минус риск потери заказов, перераспределения расходов и каннибализации.
6. Предполагаемая прибыль: `scenario_delta = contribution_after - contribution_before`; все assumptions отображать рядом.
7. Подтверждённая экономия — только после внедрения, измерения и корректной причинной проверки (контроль/holdout/каузальная методология, где применимо).
8. Любой LLM не имеет права записывать сумму в финансовое ядро или менять лимиты/права. Read-only поверх Evidence Pack, источники и JSON-schema.
9. Запрещены гарантии нахождения 100000 ₽ каждому пользователю до верификации и надлежащего юридического оформления.

## 8. UX/UI и onboarding

1. Сохрани три режима: «Начинаю» (3 главных понятных действия), «Контролирую» (финансовые причины и сверка), «Развиваю» (сценарии, приоритеты и риск).
2. Тарифы 990 / 1990 / 2990 ₽ не тождественны режимам UX; опытный клиент может открыть простой экран.
3. Разработай экран подключения WB/Ozon с пустыми состояниями, статусами ключей и предупреждениями об истечении срока; пока без настоящего ввода секретов через веб.
4. Экран статуса синхронизации: последняя дата, проверенные страницы, pending, rate-limited, failed, requires re-auth, остановлен оператором.
5. Экран evidence: дата операции, SKU, сумма, исходный отчёт, объяснение, confidence, статус подтверждения, список действий.
6. При отсутствии себестоимости блокируй «чистую прибыль» и дай понятную инструкцию добавить себестоимость.
7. Обязательно поддерживать мобильный viewport, клавиатуру, читаемость на небольшом экране и не допускать скролла внутри критичных модальных окон без индикатора.
